# ADR-0003: Poster pipeline: Slint `load_from_path` behind a small byte-budgeted LRU

- Status: Proposed
- Date: 2026-09-11

## Context

Milestone R3 adds real raster posters to the 1,000-item library. We need to
find out whether Slint stays responsive with images and whether image memory
can be kept explicitly bounded. These constraints apply:

- no network or TMDB; local synthetic assets that the Avalonia spike can reuse
  unchanged;
- decoded images must never be part of the domain model (`MediaItem`);
- no image decoding at startup beyond what the viewport needs, and no
  unbounded map of decoded images;
- no new runtime dependency unless Slint cannot do the job (R3 brief §5, §15);
- no Tokio or worker threads until measurement shows synchronous decoding
  causes jank (R3 brief §7).

Slint 1.17.1 already has what we need. `slint::Image::load_from_path` decodes
PNG and JPEG eagerly, using the `image` crate that Slint already depends on.
JPEG goes through `zune-jpeg`. The result is an owned pixel buffer: RGB8 for
opaque images, RGBA8 otherwise. `Image` is a cheap, reference-counted handle
to that buffer. `load_from_path` also has a **thread-local LRU in Slint** that
we cannot configure: 5 MiB weighted by actual pixel bytes, keyed by path and
mtime. The femtovg renderer keeps a GPU texture only while some item still
draws the image, and drops unused textures after each frame.

## Decision

1. **Assets:** 100 synthetic 240×360 baseline JPEGs (quality 85) in
   `benchmark/assets/posters/`, committed together with SHA-256 checksums.
   They are generated by `examples/generate_posters.rs`, which uses pure
   integer arithmetic and no RNG. The generator is the only user of `image` as
   a **dev-dependency**, pinned to the same 0.25.10 that Slint already
   resolves. Slint can decode images but cannot encode them.
2. **Mapping:** poster number = `(local_id − 1) % 100 + 1`, computed from the
   stable id. No schema change and no path column.
3. **Loading:** `slint::Image::load_from_path`, called synchronously on the UI
   thread from `slint::Model::row_data` (only for rows that the ListView
   instantiates) and for the detail row.
4. **Cache:** one explicit LRU owned by `LibraryView` and shared by list rows
   and the detail pane. It is keyed by poster number and bounded by an
   estimated decoded size of `width × height × 4` bytes, with a budget of
   12 MiB (36 posters). It is a plain `Vec` in recency order, not a crate. An
   image larger than the whole budget is returned but not cached. A failed
   load is remembered, so it is neither retried nor logged again.

## Alternatives considered

- **Add `image` as a runtime dependency and decode ourselves**
  (`Image::from_rgb8`): this bypasses Slint's hidden cache, so our cache would
  be the only one. It also allows decoding off the UI thread. It loses for now
  because R3 forbids a runtime image dependency while Slint can load the
  formats. It becomes the path if decoding has to move to a worker, because
  `slint::Image` is not `Send`.
- **Rely only on Slint's internal cache**: it is already a bounded LRU, but
  its 5 MiB budget cannot be configured, it has no counters, and it costs a
  `stat` on every lookup. It is also an implementation detail that could change
  under us. It fails the brief's requirement for an explicit, observable bound.
- **An external LRU crate (`lru`, `clru`)**: a hash map plus a linked list is
  more than 36 entries need. A linear scan of a `Vec` is about 40 lines and
  easy to test.
- **Store poster paths or BLOBs in SQLite**: BLOBs are out of scope, and a path
  column adds a schema change for a value that can be derived from the id.
- **PNG assets**: PNG decoding of flat synthetic art is unrealistically cheap
  (inflate of long runs). TMDB serves JPEG, so JPEG decode work is closer to
  the product.
- **Hand-written encoder or a Python/.NET generator script**: an uncompressed
  PNG is 26 MB for 100 posters. Python and .NET are off-limits on this branch.

## Consequences

### Positive

- The runtime dependency set is unchanged: Slint and rusqlite.
- The upper bound and the eviction order are explicit, observable (counters
  and a debug dump), and unit-tested apart from the GUI.
- The same `(id − 1) % 100 + 1` rule and the committed JPEGs can be used by the
  Avalonia spike as they are.

### Negative / risks

- **Two cache layers:** a miss in our cache may still be served by Slint's
  internal 5 MiB cache without decoding. Decoded pixel memory held by caches
  is therefore at most our 12 MiB estimate (at most 9 MiB of actual RGB8)
  plus Slint's 5 MiB, not the 12 MiB alone. Buffers shared by both caches are
  counted once.
- The budget is an estimate at 4 B/px. The real RGB8 buffers are 3 B/px, and
  GPU textures for visible posters live outside it.
- Decoding happens on the UI thread. A jump that brings about 10 new rows into
  view (End, Home) decodes about 10 posters in one frame.
- A failed poster is not retried until the app restarts.
- The spike reads posters from the checkout it was built from
  (`CARGO_MANIFEST_DIR`). Packaging (R5) must decide the real asset location.

## Validation

- Unit tests for hit/miss/eviction/LRU order, the budget invariant, the
  oversize and failure policies, and releasing evicted values.
- A headless Slint test (software renderer) showing that the first frame
  requests about the number of visible posters, not 1,000, and that a model
  reset over the same rows is served from cache.
- Informal release-build decode timings and a scripted long-scroll memory
  observation (`docs/measurements/R3-posters-informal.md`), plus direct
  observation of scrolling.

## Revisit trigger

- A poster miss burst regularly exceeds a 16.7 ms frame, or visible hitching
  during scrolling. Then decode off-thread, which needs `image` as a runtime
  dependency (see alternatives).
- Larger posters, a grid view, or a high-DPI detail pane that needs a
  different budget or a second resolution.
- Slint exposes control over its internal image cache.
