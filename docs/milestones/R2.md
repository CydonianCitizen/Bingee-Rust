# R2 — SQLite vertical slice

Invoke with `/milestone R2`.

## Goal

Replace the in-memory-only source of library results with a **small, real
SQLite persistence path**. Keep the R1 desktop UX and the deterministic
1,000-item dataset unchanged. This is still a technology spike: do **not**
design the final Bingee database.

The milestone must answer:

- how cleanly SQLite integrates with the Rust architecture;
- whether realistic local queries remain effectively instantaneous;
- how much complexity persistence introduces;
- whether the current UI model can remain simple.

## 1. SQLite technology choice

Prefer a direct, mature binding such as `rusqlite` unless there is a concrete
reason not to. No full ORM for convenience. Before implementing, record an ADR
covering: the chosen crate, why it fits the spike, alternatives considered,
bundled vs system SQLite, portability on Windows/macOS/Linux, impact on
binary/package size, and why a larger ORM was not chosen. Make no footprint
claims until measured.

## 2. Spike database location

- No hard-coded, developer-specific absolute path.
- Platform/path handling isolated from query logic.
- Test databases easy to create and destroy.
- No production settings/data-directory abstraction yet.

A temporary or simple application-local database is fine if documented as
spike behavior.

## 3. Minimal schema

Only what the R2 workload needs. Conceptually:

```sql
media (
    local_id       INTEGER PRIMARY KEY,
    title          TEXT NOT NULL,
    original_title TEXT NOT NULL,
    year           INTEGER NOT NULL,
    media_type     TEXT NOT NULL,
    status_text    TEXT NOT NULL,
    overview       TEXT NOT NULL,
    progress_value INTEGER,
    progress_total INTEGER
)
```

Field names and types may change where the Rust/SQLite mapping benefits. Not
yet: external refs, seasons, episodes, ratings, genres, release events, watch
history, migrations framework, backup tables.

## 4. Seed from the R1 generator

On a fresh database: create the schema and insert exactly the same 1,000
`generate_library()` records with their stable ids. Never insert duplicates on
later launches. Seeding must be deterministic and idempotent. No second
handwritten dataset.

## 5. Library query

Real SQL-backed query: a blank query returns all 1,000 records; title and
original-title search are case-insensitive; ordering is deterministic and
matches R1. Use parameterized SQL, never string concatenation. No full-text
search unless measurement shows plain SQL is insufficient.

## 6. Reference correctness

The R1 in-memory search is the reference oracle. Tests compare SQLite results
against it: empty search, normal title search, case variations,
original-title search, no match, and a query with multiple results. Same ids,
same order, unless a difference is intentional and documented. Keep the pure
Rust search.

## 7. UI integration

Keep R1 behavior: 1,000 title count, search, selection, detail pane, empty
state, keyboard navigation, and the virtualized list. No visible redesign. No
SQLite types in Slint: the presentation boundary stays plain Rust / Slint model
data.

## 8. UI-thread policy

Do not add Tokio, worker threads, or an async abstraction by default. Start
with the simplest correct query path, then measure or observe it. If it is
effectively instantaneous, keep it and document the observation. If blocking
is clearly observable, apply the smallest fix and document the evidence.

## 9. Connection ownership

Simple and explicit: no mutable global connection, no service locator, no
hidden singleton, no connection pool without measured need. The lifecycle
should be clear from a small amount of code.

## 10. Failure behavior

Handle open, schema-creation, seed, and query failures. Never silently turn a
data failure into an empty library. No `unwrap()`/`expect()` on realistic
database failure paths. A simple user-visible or startup error is enough.

## 11. Tests

Schema creation; the seed inserts exactly 1,000 records; a second seed adds no
duplicates; stable ids survive persistence; Movie/TV round-trip; a blank query
returns 1,000; case-insensitive title query; original-title query; no-match
query; deterministic ordering; SQLite matches the R1 reference; invalid
media-type handling if the mapping can encounter it. Use isolated
temporary/in-memory databases and never touch the developer's spike database.

## 12. Dependency discipline

The SQLite crate is expected. No ORM, migration framework, async runtime,
connection pool, logging framework, serialization framework for mapping, or
TMDB/network dependencies. Report exact resolved versions and the
dependency-graph increase.

## 13. Performance observation

Not the R4 benchmark. Record an informal release-build observation of fetching
all 1,000, a multi-result search, and a no-result search: build profile,
method, sample count, warm/cold cache. No conclusions about the stack.

## 14. Preserve virtualization

Confirm the Slint `ListView` still creates only visible row components.

## 15. Out of scope

TMDB, HTTP, Tokio (without R2 evidence), the final schema, migrations,
seasons/episodes, genres, ratings, statistics, release events, real posters,
image cache, notifications, backup/restore, Android sync, production packaging,
Rust-vs-Avalonia conclusions.

## 16. Verification

`rustc --version`, `cargo --version`, `cargo fmt --check`, `cargo check`,
`cargo test`, `cargo clippy --all-targets --all-features -- -D warnings`,
`cargo build --release`. Then check manually: first run seeds, 1,000 titles, no
duplicates on the second run, search, original-title search, the no-result
state, selection/details, keyboard navigation, smooth scrolling, data kept
across restarts, no unexpected errors, and database files not added to git.

## 17. Documentation

Record the crate choice, the database location, how seeding works, the limits
of the temporary schema, and an explicit statement that this is not the final
Bingee schema.

## Exit criteria (`IMPLEMENTATION_PLAN.md`)

- The app shows and queries library data from SQLite.
- Query behavior is deterministic and benchmarkable.
- The UI stays responsive.
